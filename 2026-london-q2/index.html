AI-assisted development is quickly becoming an expectation rather than a choice. Under constant pressure to deliver faster, engineers increasingly delegate not just implementation, but exploration, learning, and design thinking to AI tools. Adefisayo Adejumo

I Locked My Laptop. My Agent Never Did

Full Stack Engineer
Early in my backend career, I worked alone on systems handling real money and real users. I locked my laptop before leaving my desk, not because a policy required it, but because an unattended terminal with database access is an unguarded door. Then we started deploying LLM agents, and nobody locked anything. Today, many agents operate as permanent unattended sessions with production credentials. They call APIs, read data, and execute actions inside real systems without scoped identity, attribution, or runtime approval. In practice, an LLM agent connected to tools is an unattended session with system access. The engineers wiring agents to production systems are making security decisions by default. This talk makes those decisions deliberate. It introduces the LAR framework: Lock, Attribute, Require — three practical backend patterns for governing LLM agents at runtime. Lock. Agents should not hold standing credentials. Instead, systems generate dynamic, task-scoped credentials that exist only for the duration of an agent session. This reduces the blast radius of a compromised agent and applies the same principle engineers follow when locking their terminals. Attribute. Every agent action must be traceable. Using OAuth identity federation and delegated scopes, tool calls carry identity context so that logs clearly show which user initiated the request, which agent executed it, and what permissions were granted at that moment. Require. Certain actions should never be executed automatically. Destructive changes, financial transactions, or sensitive operations should pause until a human explicitly authorises them. Using approval flows such as Client-Initiated Backchannel Authentication, agents can request permission before completing irreversible tasks. The talk includes a live Python demonstration comparing two versions of the same LLM-powered backend agent. The first runs with permanent credentials, broad access, and no attribution. The second operates under the LAR framework with session-scoped credentials, identity propagation through tool calls, and human approval for sensitive operations. Attendees see the difference between an ungoverned agent and a governed one interacting with the same production-like environment. Key takeaways for attendees: - A clear mental model for governing LLM agents using the LAR framework: Lock, Attribute, Require - Practical patterns for implementing session-scoped credentials for agents in Python to avoid long-lived access tokens - How to use OAuth identity federation to attribute agent tool calls to the initiating user and agent identity - How to introduce human-in-the-loop approval for high-risk agent actions before execution - A practical understanding of the architectural difference between an ungoverned agent and a governed production agent A practical understanding of the architectural difference between an ungoverned agent and a governed production agent I locked my laptop. It is time we built systems that do the same.... Read more

Mingxuan Zhao

Your RAG Pipeline Is Only as Good as Your Parser: Document Processing with Docling

IBM
If you've built RAG over PDFs, you know the problem. You pick a good embedding model, pay for a good LLM, and retrieval still returns garbage because the parser mangled the tables and chunked a footnote into the middle of a paragraph. This talk is about Docling, an open-source Python library for parsing documents into something an LLM can actually use. It handles more than ten file formats, preserves structure like hierarchy and tables, and uses deep learning models to read documents closer to how a person would. The output is a structured format called DoclingDocument, and once your documents are in that shape, a lot of downstream work gets easier. Chunking is the obvious example: instead of splitting on token counts and hoping for the best, you can chunk along the document's actual structure, keeping tables intact and respecting section boundaries. I'll cover how Docling works, show a parsing-to-retrieval pipeline built on structure-aware chunking, and walk through docling-agent, a newer project that skips chunking entirely. Instead of pre-chunking and embedding, the agent navigates the DoclingDocument structure at query time, which is an interesting answer to a problem chunking has always papered over. Docling is MIT-licensed and runs locally, which matters when your documents can't leave your environment or you care about latency. For engineers building RAG, agents over documents, or anything that starts with "get the text out of this PDF." Python familiarity assumed, no ML background needed.... Read more

Nuno Campos

Teaching Coding Agents to Master Spreadsheets

Witan Labs
Where an analyst sees a revenue table and a P&L summary, an LLM sees 10,000 cell values and nested SUMPRODUCT formulas. Over four months we pushed our agent's pass rate from 50% to 92%, through several architectures, many dead ends, and one decision that mattered more than the rest: replacing fifteen discrete tools with a single persistent Node.js REPL. This talk is a field report on what worked and what didn't. The REPL lets the agent write JavaScript instead of stringing tool calls together, with variables that persist so it can explore, reason, and course-correct mid-task. Underneath sits a verification loop — formula calculation, rendering, linting - that the agent uses to check its own work, and that has compounded across three frontier model releases rather than been made redundant by them. The lessons generalise: interfaces are ephemeral but verification engines are durable, domain knowledge outlasts tooling (we changed backends four times; the financial-domain prompt carried over every time), evaluation is roughly half the work, and most "agent confusion" is really a plumbing problem... Doubleword
As models improve, we are starting to build long-running, asynchronous agents such as deep research agents and browser agents that can execute multi-step workflows autonomously. Adefisayo Adejumo

Full Stack Engineer
I Locked My Laptop. My Agent Never Did
Abstract

Early in my backend career, I worked alone on systems handling real money and real users. I locked my laptop before leaving my desk, not because a policy required it, but because an unattended terminal with database access is an unguarded door. Then we started deploying LLM agents, and nobody locked anything. Today, many agents operate as permanent unattended sessions with production credentials. They call APIs, read data, and execute actions inside real systems without scoped identity, attribution, or runtime approval. In practice, an LLM agent connected to tools is an unattended session with system access. The engineers wiring agents to production systems are making security decisions by default. This talk makes those decisions deliberate. It introduces the LAR framework: Lock, Attribute, Require — three practical backend patterns for governing LLM agents at runtime. Lock. Agents should not hold standing credentials. Instead, systems generate dynamic, task-scoped credentials that exist only for the duration of an agent session. This reduces the blast radius of a compromised agent and applies the same principle engineers follow when locking their terminals. Attribute. Every agent action must be traceable. Using OAuth identity federation and delegated scopes, tool calls carry identity context so that logs clearly show which user initiated the request, which agent executed it, and what permissions were granted at that moment. Require. Certain actions should never be executed automatically. Destructive changes, financial transactions, or sensitive operations should pause until a human explicitly authorises them. Using approval flows such as Client-Initiated Backchannel Authentication, agents can request permission before completing irreversible tasks. The talk includes a live Python demonstration comparing two versions of the same LLM-powered backend agent. The first runs with permanent credentials, broad access, and no attribution. The second operates under the LAR framework with session-scoped credentials, identity propagation through tool calls, and human approval for sensitive operations. Attendees see the difference between an ungoverned agent and a governed one interacting with the same production-like environment. Key takeaways for attendees: - A clear mental model for governing LLM agents using the LAR framework: Lock, Attribute, Require - Practical patterns for implementing session-scoped credentials for agents in Python to avoid long-lived access tokens - How to use OAuth identity federation to attribute agent tool calls to the initiating user and agent identity - How to introduce human-in-the-loop approval for high-risk agent actions before execution - A practical understanding of the architectural difference between an ungoverned agent and a governed production agent A practical understanding of the architectural difference between an ungoverned agent and a governed production agent I locked my laptop. It is time we built systems that do the same.

Mingxuan Zhao

IBM
Your RAG Pipeline Is Only as Good as Your Parser: Document Processing with Docling
Abstract

If you've built RAG over PDFs, you know the problem. You pick a good embedding model, pay for a good LLM, and retrieval still returns garbage because the parser mangled the tables and chunked a footnote into the middle of a paragraph. This talk is about Docling, an open-source Python library for parsing documents into something an LLM can actually use. It handles more than ten file formats, preserves structure like hierarchy and tables, and uses deep learning models to read documents closer to how a person would. The output is a structured format called DoclingDocument, and once your documents are in that shape, a lot of downstream work gets easier. Chunking is the obvious example: instead of splitting on token counts and hoping for the best, you can chunk along the document's actual structure, keeping tables intact and respecting section boundaries. I'll cover how Docling works, show a parsing-to-retrieval pipeline built on structure-aware chunking, and walk through docling-agent, a newer project that skips chunking entirely. Instead of pre-chunking and embedding, the agent navigates the DoclingDocument structure at query time, which is an interesting answer to a problem chunking has always papered over. Docling is MIT-licensed and runs locally, which matters when your documents can't leave your environment or you care about latency. For engineers building RAG, agents over documents, or anything that starts with "get the text out of this PDF." Python familiarity assumed, no ML background needed.

Nuno Campos

Witan Labs
Teaching Coding Agents to Master Spreadsheets
Abstract

Where an analyst sees a revenue table and a P&L summary, an LLM sees 10,000 cell values and nested SUMPRODUCT formulas. Over four months we pushed our agent's pass rate from 50% to 92%, through several architectures, many dead ends, and one decision that mattered more than the rest: replacing fifteen discrete tools with a single persistent Node.js REPL.

This talk is a field report on what worked and what didn't. The REPL lets the agent write JavaScript instead of stringing tool calls together, with variables that persist so it can explore, reason, and course-correct mid-task. Underneath sits a verification loop — formula calculation, rendering, linting - that the agent uses to check its own work, and that has compounded across three frontier model releases rather than been made redundant by them.

The lessons generalise: interfaces are ephemeral but verification engines are durable, domain knowledge outlasts tooling (we changed backends four times; the financial-domain prompt carried over every time), evaluation is roughly half the work, and most "agent confusion" is really a plumbing problem

Max Helzberg

Northslope Technologies
Purpose-Built AI Ontologies: Why Data Modeling Determines LLM Performance
Abstract

Large language models are often treated as the center of modern AI systems, but in enterprise deployments the real performance ceiling is set much earlier — at the data modeling layer. In this talk, Max Helzberg draws on experience building operational AI systems in complex environments to show why domain-specific ontologies and semantic data models are critical for reliable LLM and agent performance. When models interact with messy operational data, poorly structured schemas lead to hallucinations, brittle reasoning, and systems that fail in production. The session explores how purpose-built ontologies differ from traditional data warehouses, and how those differences influence downstream model behavior. Topics include entity resolution at scale, semantic relationships between operational objects, and how structured action hierarchies enable reliable agent workflows. Through real-world examples from sectors such as energy, finance, and national security, the talk highlights common failure modes in enterprise AI systems and shows how carefully designed semantic layers dramatically improve reasoning quality, traceability, and auditability. Attendees will leave with practical insights into how data architecture choices influence the success of LLM applications — and why the most important design decisions for AI systems often happen long before model training begins.
